 1. GRADING  — "each task should grade perfectly"
================================================================================

THE BUG THAT WAS THERE
  Each task's score came from a title → points map that lived in a separate
  grader module from the Jest spec it described. Grading matches on the test's
  TITLE STRING. Rename a title, or typo a key, and the test still runs, still
  passes — and silently scores 0. A perfect submission caps below 100 and
  nothing anywhere reports a problem.

  All five existing maps happened to be correct. The arrangement was one edit
  away from not being, and adding four more tasks would have quadrupled the
  surface.

WHAT CHANGED
  app/services/frontend_specs.py        REWRITTEN
      Spec and points now live together in one FrontendTaskSpec per task.
      validate_specs() parses the titles back out of the spec source and
      asserts: every test is scored, every score maps to a real test, no
      duplicate titles, and the total is exactly 100.

  app/services/graders/frontend_tasks.py    NEW
      One make_grader(index) generating all nine graders from the specs, so a
      task cannot exist without its grading also existing.
      DELETED: frontend_task1.py … frontend_task5.py (five near-identical
      copies of the same two lines).

  app/services/graders/registry.py      grader keys now generated, not listed.

VERIFICATION — three layers, all run

  a) tests/unit/test_frontend_specs.py (NEW)
     Every spec fully scored and totalling 100; a synthetic all-pass report
     scores 100 and an all-fail scores 0, per task.

  b) verify_frontend_grading.py (NEW) — the real Docker sandbox
     Runs each task's worked solution AND its untouched starter through the
     actual container. The starter check is the one that proves the suite
     measures anything: a spec that passes on the stub asserts nothing.

         task 1  OK  solution=100  starter= 45   Landing Hero Section

 2. TASK CONTENT  — beginner and advanced, in the same page
================================================================================

  A new config.explainer block per task, replacing the bullet list:

      situation   why this work exists, in plain language
      outcome     what "finished" looks like, concretely
      preview     a monospace sketch of the finished result
      concepts    new ideas DEFINED BEFORE they are used  ← the beginner layer
      steps       each with `plain` and `deeper`
      contract    the exact identifiers the hidden tests require
      mistakes    the specific ways this task goes wrong
      further     ungraded extensions                     ← the advanced layer

  The two-track design, which is the point of the redesign:

      plain   — written for someone who has never done this, using no
                vocabulary that hasn't been defined on the page.
      deeper  — the trade-off, failure mode, or reason it's done this way.
                Collapsed behind a "Going deeper" toggle.

  Neither summarises the other. A beginner can read only the plain text and
  finish the task. An experienced developer can read only the deeper notes and
  still learn something. The single middle-pitched explanation that a bullet
  list forces bores one reader and loses the other.

  Sample of the `deeper` layer, so the register is clear:
    · "sort() and reverse() mutate in place — a function that silently
       reorders its caller's array causes bugs a long way from the mistake."
    · "Everything before the first await runs synchronously; after it, control
       returns to the browser — which is why a loading state set afterwards
       appears only once the data has already arrived."
    · "Mutating task.completed leaves the same object in the same array, so
       React sees nothing changed. Immutability isn't style here; it's the
       mechanism by which change is detected."
    · "alt='' and omitting alt are NOT the same — a missing alt makes many
       screen readers read the filename aloud."

  Content authored per task: situation, outcome, ASCII preview, 4–5 concepts,
  3–5 two-layer steps with code samples, a contract table, 4–6 mistakes,
  3 extensions, plus starter code, a fully commented worked solution, and a
  5-question assessment.

 4. ASSESSMENTS  — graded on the server, not in the browser
================================================================================

  The existing post_task_quiz path grades in the browser, which requires
  shipping the correct answers to the browser to do it. Acceptable for a
  low-stakes check. Not acceptable for something called an assessment, least
  of all a 50-question final that gates a certificate.

  So `config.assessment` is a SECRET config key for both code_sandbox and quiz
  types — stripped from the public simulation payload entirely.

      GET  /api/enrollments/{id}/tasks/{n}/assessment   questions, no answers
      POST /api/enrollments/{id}/tasks/{n}/assessment   answers in, result out

  `correct` and `explanation` are returned only by the POST, once the attempt
  is committed and can no longer be changed.

  Verified live against the real database:
      GET /full           assessment leaked on: []   grader_key leaked on: []
      GET assessment      q0 keys: ['index','options','question']
      POST short          400  "Expected 5 answers, got 1"
      POST all-blank      200  score 0, explanations returned
      POST all-correct    200  score 100
      GET final           200  50 questions, pass_mark 70

  A BUG IN MY OWN ENDPOINT, FOUND BY THAT SMOKE TEST AND FIXED
      Submitting the mini assessment for a sandbox task that had NOT been
      graded fell through to award_task_completion — marking the coding task
      complete, awarding its full XP, recording the quiz percentage as the code
      score, and unlocking the next task, for a student who never opened the
      editor. Now returns 409 "Submit the task before taking its assessment".
      Only a standalone quiz task (the final) may complete itself.

  WHERE THE ASSESSMENT APPEARS
      · Automatically, in the sandbox tab, the moment a submit is graded —
        that is what "conducted when the task is completed" means, and an
        assessment you must navigate elsewhere to find is one nobody takes.
      · Skippable on purpose. A check you can't decline is a gate; this is
        meant to consolidate, not to block the next ticket.
      · Also on the task page, and flagged on the roadmap when untaken.

  QUESTION BANK
      45 mini-assessment questions + 50 final. Every one carries an
      explanation — the difference between a score and a lesson. The final
      ramps from "which element wraps the primary content" to reviewing a PR
      that adds 400KB to format one timestamp.

 6. TWO THINGS FIXED THAT WEREN'T ASKED FOR
================================================================================

  THE BACKEND TEST SUITE WAS ENTIRELY UNCOLLECTABLE.
      pytest.ini sets asyncio_default_fixture_loop_scope = session, an option
      that only exists in pytest-asyncio 0.24+. Installed: 0.21.1, which
      ignores unknown ini keys — so the session-scoped _test_database fixture
      depended on a function-scoped event_loop and EVERY test errored at setup
      with ScopeMismatch. Not one backend test could run.

      Fixed with a session-scoped event_loop override in conftest.py, the
      documented 0.21 approach. Remove it when pytest-asyncio is upgraded.
      Result: 115 passed. It had to be fixed — grading tests that cannot run
      prove nothing.

  A CONFIG KEY NOT IN A SCHEMA IS SILENTLY ERASED.
      validate_task_config round-trips config through a pydantic model, and
      pydantic DROPS unknown fields. `explainer` and `assessment` would have
      been wiped the first time an admin opened a task in the CMS builder and
      pressed save — no error, no warning, content simply gone. Both now have
      real schemas, with a test asserting they survive the round trip.

 8. EDITOR PUSHED OFF THE WINDOW WHEN DRAGGING
--------------------------------------------------------------------------------
ASKED   Dragging the description moves the editor content off the window.

MY ERROR #4 — MISSING min-w-0
        A flex item defaults to min-width: auto and refuses to shrink below its
        content's intrinsic width. The editor column had no min-w-0, so as the
        brief grew the column held its width and the editor slid off the right
        edge. Nothing about min-w-0 looks like a sizing rule, which is why it is
        easy to omit and hard to spot afterwards.

ALSO    The drag ceiling was a design-time guess (max=760). Now derived from the
        container's live width via ResizeObserver, and clamps back down when the
        window shrinks so a size stored on a big monitor does not strand you on
        a laptop. Toolbar made to scroll and the filename to truncate so neither
        sets the editor's minimum. overflow-hidden as a backstop.

MY ERROR #5 — BUG IN THAT FIX, CAUGHT BEFORE SHIPPING
        First version used useRef for the observed element. The container mounts
        after several early returns, so the effect ran once against null and
        never re-ran — a ref object's identity never changes, so the dependency
        never fires again. splitWidth would have stayed 0 and the "dynamic"
        ceiling silently fallen back to the old hardcoded 760 forever. Replaced
        with a callback ref holding the node in state.

 27. MENTOR REPLIES RENDERING AS RAW MARKDOWN TABLES
--------------------------------------------------------------------------------
REPORTED  The AI mentor answered with unformatted output — pipe tables printed
          as literal text, emoji-numbered headings, one unreadable wall.

CAUSE — LATENT SINCE BEFORE THE MODEL CHANGE
        ChatMessage.jsx already rendered markdown through react-markdown. But
        react-markdown only implements CommonMark, which HAS NO TABLES. Tables
        come from `remark-gfm`, which was never installed — not in
        package.json, not in node_modules.

        So a pipe table always fell through as literal text. It was invisible
        while the old model answered in prose, and became obvious the moment
        the provider model changed to gpt-oss-120b, which formats with tables
        by preference. The model change exposed it; it did not cause it.

        Two of the three AI panels were worse still: TaskMentorPanel and
        SandboxAiPanel rendered replies with `whitespace-pre-wrap`, so even
        bold and lists came through as raw ** and -.

FIXED — RENDERER
        npm install remark-gfm
        New components/ui/MarkdownMessage.jsx — one renderer for all three
        panels (global mentor, task rail, sandbox assistant) so they cannot
        drift apart again. Tables get their OWN overflow-x-auto container: a
        table that cannot shrink below its content pushes a chat bubble wider
        than its column and breaks the layout.
        User messages and error text stay literal — rendering a student's own
        input as markdown would mangle any code or asterisks they typed.

FIXED — PROMPT
        Rendering a 6-column table correctly still leaves it unreadable in a
        22rem panel. Added a Formatting section to build_system_prompt():
        prefer bullets, NO tables, headings no larger than ###, no decorative
        emoji, fenced code with a language tag.

        4 new tests on MarkdownMessage, including that a GFM table becomes a

FOUND     backend/logs/backend.log, one grep:

          The guard was:

            if not hasattr(sim, "university_links") or sim.university_links is None:
                await db.refresh(sim, attribute_names=["university_links"])

          On an async session, touching an UNLOADED relationship attribute
          triggers a lazy load with no greenlet to run it in, and SQLAlchemy
          raises MissingGreenlet. That is not an AttributeError, so hasattr()
          does NOT swallow it.

          The guard written to AVOID the load was the thing performing it, and
          it raised on every call. Reproduced directly:

            university_links unloaded?  True
            hasattr(...)             -> RAISES MissingGreenlet

          assert_sim_visible_to_tenant runs on exactly three routes:

            GET  /api/simulations/{slug}/onboarding
            POST /api/simulations/{slug}/enroll
            POST /api/simulations/{slug}/onboarding/accept

          which is the entire path between the overview page and a simulation
          opening. Every sim, every student, 500.

WHERE IT CAME FROM
          simulation_scope.py arrived in the origin/main merge (entry 33's
          conflicts). My verification after that merge exercised
          /api/simulations (the list) and /api/skill-gps — neither calls this —
          so the suites and my smoke tests were all green over a dead path.
          The lesson is specific: after merging a file that adds a shared
          helper, test the ROUTES that call it, not the ones that happen to be
          nearby.

FIXED     Both readers now use the inspection API instead of attribute access:

            if "university_links" in sa_inspect(sim).unloaded:
                await db.refresh(sim, attribute_names=["university_links"])

          `scope_payload`, ten lines above in the same file, was ALREADY doing
          it correctly — the file disagreed with itself. Its local
          `from sqlalchemy import inspect` was hoisted to the module so both
          share one import.

          sim_visible_to_university had the same latent trap via
          `getattr(sim, "university_links", None)` — a getattr default cannot
          catch MissingGreenlet either. It now checks `unloaded` first and
          treats an unloaded relationship as "not visible": the scoped case
          cannot be answered without the links, and refusing is the safe
          direction for a visibility check. Its docstring now states that it
          performs no IO, which is the property that makes it callable from
          sync code at all.

          Swept for the same pattern elsewhere: no other hasattr() on a
          relationship anywhere in app/, and the only two remaining reads of
          .university_links both sit behind an `unloaded` check.

  Added verbatim as `.cube-loader` — only the class name changed, namespaced so

  There was already a 5s ceiling on the opening state, cleared early by the
