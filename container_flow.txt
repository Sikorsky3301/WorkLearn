HOW THE DOCKER CONTAINER RUNS — FROM "START SANDBOX" TO GRADED RESULT
======================================================================

IMPORTANT FIRST FACT
---------------------
Clicking "Start Sandbox" does NOT create a container. It is a purely
client-side UI gate: the button sets a "starting" flag, waits 900ms
(a fake delay with a "Provisioning an isolated container..." message),
then reveals the code editor. No API call happens at this step. No
Docker container exists yet.

The real container is only created later, when the student clicks
Run, Submit for Grading, or Upload a file.

(File: src/features/simulations/JupyterPlayground.jsx)


STEP-BY-STEP FLOW (Run / Submit / Upload)
------------------------------------------

1. STUDENT CLICKS RUN OR SUBMIT
   The browser sends the student's code (or an uploaded output.csv) to:
     POST /api/sandbox/{enrollment_id}/tasks/{task_id}/submit
   Body: { code, dry_run } or { output_csv (base64), dry_run }
   dry_run = true for "Run" (a free preview), false for "Submit for Grading"
   (which persists the score to the database).

2. BACKEND RESOLVES THE INPUT DATASET
   FastAPI route app/routes/sandbox.py figures out what dataset.csv the
   sandbox should see:
     - Task 1: the raw seeded lumen_orders dataset (deterministically
       generated from the student's enrollment ID, so every student gets
       a different but reproducible dataset).
     - Tasks 2-4: the student's own Task 1 cleaned output (never the raw
       data), previously saved as an artifact on disk.

3. BACKEND HANDS OFF TO THE SANDBOX FACADE
   app/services/sandbox.py picks a runner based on the SANDBOX_RUNNER
   setting (defaults to "docker"):
     - "docker" -> app/services/sandbox_runners/docker_runner.py (this
       is the path described below; used for local/dev deployments)
     - "kubernetes" -> app/services/sandbox_runners/k8s_runner.py
       (launches a Kubernetes Job pod instead of a local container;
       used when the backend itself runs inside a cluster)

4. A FRESH TEMP WORKDIR IS CREATED
   docker_runner.py creates a new temporary directory on the host
   (tempfile.mkdtemp) and writes into it:
     - submission.py   <- the student's code
     - dataset.csv      <- the resolved input data

5. THE CONTAINER IS LAUNCHED
   The backend runs this exact command (via subprocess, offloaded to a
   worker thread so it doesn't block the API server):

     docker run --rm
       --network=none
       --memory=256m
       --cpus=0.5
       --pids-limit=64
       --cap-drop=ALL
       --security-opt=no-new-privileges
       -v {workdir}:/workspace
       worklearn-sandbox-python:latest

   What each flag buys:
     --rm                    container is deleted automatically on exit
     --network=none           no internet/network access at all
     --memory=256m             hard memory cap
     --cpus=0.5                 half a CPU core cap
     --pids-limit=64            can't fork-bomb the host
     --cap-drop=ALL              no Linux capabilities beyond baseline
     --security-opt=no-new-privileges   can't escalate privileges
     -v {workdir}:/workspace      the ONLY way the container exchanges
                                    files with the host

6. INSIDE THE CONTAINER
   The image's entrypoint (sandboxes/python/entrypoint.py, running as a
   non-root user, uid 10001) does exactly one thing: exec the student's
   submission.py against dataset.csv, with matplotlib in headless mode.
   Whatever the code writes to /workspace/output.csv or output.json is
   the only thing that will ever be graded — printed stdout is never
   trusted as the source of truth, only captured for the student to see.

7. THE 15-SECOND BUDGET
   The backend waits up to 15 seconds (settings.sandbox_timeout_seconds)
   for the container to finish. If it hasn't finished in time, the
   backend kills the docker process, the container is forcibly stopped,
   and the response is marked timed_out=true with no output graded.

8. CONTAINER EXITS AND IS AUTO-REMOVED
   Normal exit or timeout, the container is gone the moment it stops
   (--rm). Nothing lingers on the host as a running or stopped container.

9. BACKEND READS THE RESULT BACK
   The backend reads output.csv or output.json straight out of the temp
   workdir on the host filesystem (not from inside the container, which
   no longer exists) and grades it against a server-computed reference
   solution. The grader never trusts anything the student's code printed.

10. CLEANUP
    The temp workdir is deleted (shutil.rmtree) in a "finally" block,
    whether grading succeeded, failed, or timed out.

11. PERSISTENCE RULE
    If dry_run=true (the student clicked "Run"), nothing is saved —
    it's a free, repeatable preview. Only a real "Submit for Grading"
    (dry_run=false) writes the output artifact to disk and records the
    score/XP in the database.

12. RESPONSE BACK TO THE BROWSER
    The grade result (score, per-check pass/fail, stdout/stderr,
    timed_out flag) is sent back to the frontend, which reveals the
    test cases one at a time with a short animation before showing the
    final score.


ONE CONTAINER PER SUBMISSION
------------------------------
There is no persistent "student's container" sitting around waiting.
Every single Run, Submit, or Upload click is its own brand-new,
short-lived container: created, executed, and destroyed within
(at most) about 15 seconds. Two students clicking Run at the same
moment get two completely separate, isolated containers with no
shared state between them.
